## Summary

Switch (the Hermes-agent replacement) runs its own copy of Mnemosyne under `~/.switch/memory/` and must never read or write `~/.claude`. The engine is not Claude-specific: `engine/` is a vendored copy of `@oh-my-pi/pi-mnemopi` 18.12.3 from oh-my-pi (`engine/UPSTREAM.md:3-5`) and nothing in `engine/src` needs `.claude` (the only mention is a comment at `engine/src/core/embeddings.ts:65`). The Claude coupling is in the plugin layer. The work: move the launcher template and the owner formula out of `hooks/register.ts` into host-free modules, make the model cache folder a parameter, add `--root` to the installer with a lock, add an owner CLI, and add one error field.

## Facts the plan rests on (checked in the source on 2026-10-31 and confirmed by the review)

1. `hooks/register.ts` imports `atom, read, update` from `claude-code` at runtime (`:15`) and calls `atom()` at import time (`:147`, `:150`). A plain script cannot import it (`Cannot find module 'claude-code'`; it loads only with a 3-export stub). `shWrapper` (`:518`), `cmdWrapper` (`:550`), `shellQuote` (`:476`), `WRAPPER_NOTE` (`:510`), `owner()` (`:457`), `GLOBAL_OWNER` (`:110`) and `slashes` (`:281`, 24 uses) are not exported. `hooks/ui-launch.ts:17` also names `claude-code`, but only as `import type` (erased), so `register.ts:15` is the only runtime host import in `hooks/` and `bin/`. [F11 wording]
2. The proxy's import closure is exactly 11 files, no dynamic `import()`, no `claude-code`: `bin/mcp-proxy.ts`, `bin/activity.ts`, `bin/settings.ts`, and `hooks/{activity-log,engine-build,guard,kinds,settings,surface,tags,vocab}.ts` (`hooks/vocab.ts` imports `./tags`). The review copied those 11 files to a bare folder and ran the proxy from `/`: `initialize`, `tools/list`, remember and recall all worked. The proxy refuses saves when the installed engine version differs from `ENGINE_BUILD` (`bin/mcp-proxy.ts:185`).
3. The default model cache string `.claude/mnemosyne/model-cache` is one literal, `EMBEDDINGS_CACHE_DIR` (`hooks/engine.ts:15`), used by `engineEnv` (`:81`), `shWrapper` (`hooks/register.ts:540`) and `cmdWrapper` (`:573`), plus a second independent literal in `bin/install-engine.ts:145`. The engine resolves `PI_CONFIG_DIR` with `path.resolve(homedir(), configDir)` (`engine/src/core/embeddings.ts:74-81`): absolute gives `<dir>/cache/fastembed`, relative gives `<HOME>/<dir>/...`, unset gives `<HOME>/.omp/...`. So an absolute path needs no engine change. [F11]
4. `bin/install-engine.ts` already stages into `<engine>.next`, runs a real check, swaps with `.old` rollback and restores `.old` after a crash. Its CLI is positional `[pluginRoot, engineDir, storeDir, embeddings]`, with no `--root`, no lock, no same-build early return (a second run is a full reinstall). Its check sends `tools/list` as id 1, then remember and recall with embeddings, and does not send `initialize` first (`:150-156`); the engine answers `tools/list` without it. The four `@oh-my-pi` dependencies and `fastembed` come from npm at install time; the installed engine has no lockfile (the repo has them).
5. Owner formula (`register.ts:457-464`): `global` unless scope is `per-project`; else the repo root (host `session.repo()`), or the cwd; slashes normalised; hash starts at 5381, `hash = ((hash*33) ^ charCode) >>> 0` per code point, taking the first UTF-16 unit; id = `project-<last folder, non-alphanumeric runs to "-">-<hash base 36>`. An astral character hashes differently from a per-unit loop (`😀` gives `yhodqn`, per unit `pk60f`).
6. Guard errors: `-32602` with `data: { rules }` at `bin/mcp-proxy.ts:203` (block, including secret and size blocks) and `:216` (warn, strict or chatter, no `confirm`). Other `-32602` errors (`:231`, `:236`, `:242`, `:252`, `:258`) carry no data and stay as they are. The build-mismatch refusal is `-32000` (`:187`) and its text tells the user to "Run /mnemosyne-setup in Claude Code" (wrong for Switch, see SA.5).
7. Tests: `tests/bun/{install-engine,mcp-proxy,engine-env,engine-build}.spec.ts`; the wrapper test in `tests/register.test.ts` spans `:814-841` (`:835` asserts `PI_CONFIG_DIR=.claude/mnemosyne/model-cache`, `:840` the chmod). No test calls `shWrapper` or `owner()` directly. `tests/*.test.ts` need `claude-code/testing`, which only the Claude Code host supplies: they do not run in this checkout (`Cannot find module 'claude-code/testing'`), and they are not a gate. [F1] Specs in `tests/bun` do not need an installed engine (`tests/bun/knowledge-host.ts:71-76` links `ROOT/engine`). The earlier baseline (1418 pass, 2 fail, 2 errors, 1005 s) is unverified and its stated cause was wrong; the builder records its own baseline first and reports any red test by name.
8. The repo already has a race-free lock pattern: `lock()` in `bin/activity.ts:76-103` (create with `wx`, close; on `EEXIST` and stale, rename aside to a pid-unique name, `linkSync` it back if it turned out fresh, then unlink). It is a non-waiting try-lock and is not exported. `bin/memories.ts:510-537` has the unsafe variant tracked as issue #37 (deletes the aside before checking freshness): do not copy it. [F2]
9. `tsconfig.bun.json:9` lists `hooks/` files one by one; `bin/` is included wholesale. [F15]

## Decisions

1. Owner CLI stays, as the oracle for Switch's Rust golden fixture (Switch SD10, epic §3.5 ports the formula to Rust; #43 item 5 asks for the CLI so it need not be copied). Both hold. Switch's side decides whether it keeps the Rust port. Already told to the Switch tab (2026-11-01).
2. Owner symlink rule [F8], decided here and flagged for Switch: repo root = the parent of `git rev-parse --path-format=absolute --git-common-dir`, which git returns symlink-resolved (on macOS `/tmp` becomes `/private/tmp`). The CLI hashes that root as git reports it, and a path that is not in a git repo is hashed as given (lexically normalised, never canonicalised, as epic §3.5.5 says). So for a repo reached through a symlink the CLI and a host that reports a lexical root can differ. The golden fixture uses real paths, and one extra row (symlinked path into a repo) records the divergence in the fixture so it is visible. If the builder finds the two Switch rules cannot both hold for that row, it stops and asks; it does not choose.
3. The proxy ships inside the root. `--root` copies the proxy's import closure to `<root>/plugin/{bin,hooks}`, found by a small walker over relative imports at install time (not a hard-coded list), and the launcher runs `<root>/plugin/bin/mcp-proxy.ts`. Switch then needs no checkout after setup. [F5]
4. `install-engine.ts` owns the staged install and the lock; Switch's `install.rs` clones the tag and calls it. A same-tag rerun is a full reinstall, not a no-op (changing that would stop `/mnemosyne-setup` from rebuilding after an engine change); Switch decides "already current" from its own `memory.json`. The issue asks only that one install wins and the other waits or exits cleanly. [F6]
5. The release tag is pushed by Rohit, not by a builder.
6. Windows: `cmdWrapper` moves with the launcher module and `--root` writes the `.cmd` there, untested on Windows (changelog says so, no Windows test). A `--root` or derived path containing `"`, `%` or `!` is refused on Windows, as `memoryDir` already refuses `"` and `%` (`hooks/register.ts:303`). [F7]
7. `--source <checkout>` is dropped: the checkout the script runs from is the only case Switch has. SA.2 (cache parameter) is merged into the `--root` task, since both edit the same three files. [Q5]

### SA.2 `install-engine.ts --root`, the lock, and the cache parameter
1. `engineEnv` and the install check take an optional `modelCacheDir` (default `EMBEDDINGS_CACHE_DIR`); the plugin passes nothing. A spec proves an absolute `PI_CONFIG_DIR` puts the cache at `<dir>/cache/fastembed` (no engine edit). [F11]
2. Keep the positional form working exactly as today. Add `--root <abs dir>` with optional `--store <abs dir>` (default `<root>/store`) and `--embeddings`. Under the root it creates only what is missing: `engine/`, `store/`, `model-cache/`, `plugin/{bin,hooks}` (decision 3), `bin/mnemosyne-mcp` (and `.cmd` on Windows), `config.json`, `vocabulary.json`, and the path for `activity.jsonl`. Modes on POSIX: folders 0700, the launcher 0700 (it must be executable, Switch spawns it), `config.json`, `vocabulary.json` and `activity.jsonl` 0600. [F3]
3. `config.json` (defaults, from the same settings code the dashboard uses) and `vocabulary.json` (the existing `initVocabulary(store, root)`, `bin/vocab.ts:102`, which needs the store first) are created after the engine is swapped in, only when absent; an existing one is kept byte for byte. [F4]
4. In `--root` mode nothing under `$HOME/.claude` or `~/.omp` is read or written. Refuse a `--root` inside `<engine>`, `<engine>.next` or `<engine>.old`, as the positional form does for the store. On Windows refuse `"`, `%` and `!` in the root and every derived path. [F7]
5. The check sends `initialize` (and its notification) before `tools/list`, so issue item 2's wording is literally true. [Q1]
6. Lock, both modes: `<engine>.lock` (in `--root` mode `<root>/engine.lock`). Extract the existing `lock()` from `bin/activity.ts:76-103` into a host-free `bin/lockfile.ts` as `takeLock(path, staleMs)`, with no change to `activity.ts` behaviour (its own tests stay green); the installer wraps it in a poll loop and does not write a third variant. Rules: mtime is the only stale test (a lock older than 30 minutes); the pid and time written inside are for people, and a dead pid alone never makes a lock stale; the lock file is closed immediately after creation; the holder refreshes the lock's mtime every 60 seconds while installing, so a healthy long install is never stale; the lock is released in a `finally`, also after a failed install. A second install waits up to 600 seconds (longer than the worst case of 240 s install step plus 300 s check) polling every second, then exits with code 3 and the message `another install holds <path>`. [F2, F16, F17, Q3]
7. Tests in `tests/bun/install-engine.spec.ts` (or a new spec file beside it): (a) `--root` in a temp folder with `HOME` pointed at a second temp folder holding a fake `.claude/mnemosyne` tree, hashed before and after: unchanged; (b) the same install and a launcher `initialize` with `HOME` set to a folder that does not exist, both succeed: the read proof [Q1.3]; (c) the launcher written under the root answers `initialize` and `tools/list` through the copied proxy, and its mode is 0700 with the other files 0600; (d) two installs at once: one wins, the other waits and then installs, or exits 3 with the message; (e) a stale lock (older than 30 minutes) is taken over, a fresh lock is not, a dead pid alone does not make a lock stale, and the lock is gone after a forced-failed install; (f) a forced-failed check leaves the previous engine answering; (g) config.json and vocabulary.json are created when absent and kept byte-for-byte when present; (h) the copied proxy files equal the walker's closure, and none of them imports `claude-code` at runtime [F5]; (i) the launcher under the root differs from the plugin launcher for the same options only in paths; (j) on Windows paths, a root with `"`, `%` or `!` is refused (test the check as a pure function, no Windows host needed).
8. Done: issue #43 "done when" 1 and 2 hold, shown with the real command in a temp root (embeddings off), output quoted in the report.
